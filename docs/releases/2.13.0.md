# Video Summary 2.13.0

- **Light tier: a note without a backend.** A job that carries a transcript goes straight to your summary model, with no backend and no Docker: a transcript pasted into the side panel, or the captions the browser extension sends from a YouTube page. The note appears in the job card as it is written, in the same shape as a backend note (prompt v5: title, summary, key points, timestamped transcript, evidence). A reasoning model first thinks for up to half a minute; the card says _Reading the transcript_ meanwhile. A transcript over 80,000 characters is condensed part by part first. On by default; turn it off under **Settings → Video Summary → Model → Light tier**. A link or a local file on its own still needs the backend, and the plugin says so.
- **The browser extension sends YouTube captions.** On a YouTube page, capture (⌘⇧S, the popup's button or the right-click menu) reads the captions the page's player loaded — written ones in the spoken language first, then the automatic ones — and puts them in the note as `provided_transcript`, so the plugin can use the light tier. It does not work while an ad is playing; then only the link is sent. Turn it off in the extension's settings under **YouTube 字幕**. _Send to the plugin_ now asks the plugin to process the video with `process=1`; it used to only file the link in the inbox, because Obsidian replaces a link's `action` parameter with the handler's name. Captions are found whether the player signs its request with `pot=` or `signature=`, and also when captions were already on, which are left as they were. The extension (now 0.8.0) is still loaded by hand in developer mode; after its files change, switch it off and on in `chrome://extensions`, since Chrome keeps running the scripts it loaded first. Installing it no longer asks for access to all websites: it reads only the tab you use it on and talks to Obsidian and a backend on this computer; for a backend elsewhere, Chrome asks for that one site when you save its address.
- **Notes carry only what you read.** `video_transcript`, `video_artifact_id`, `video_content_type`, `video_attention_action` and `video_processing_depth` are no longer written into properties. The transcript is a folded `> [!quote]- 原始文稿` callout at the end of the note (it was there already; now only there). The other four stay in the plugin's own records, found by the note's path, so rerunning, cached results, Insert into the current note, the reader and course import work as before. Notes that already have these properties keep working; when such a note is processed again, the old properties are removed. The Video Summary Library base no longer shows those columns.
- **Pasted articles are articles.** A note made from a pasted article or transcript, with no video link and no local file, gets `source_type: article` and the tags in the new **Article tags** setting instead of the tags in the default properties.
- **A finished job opens its note.** In the side panel, clicking a finished job (or pressing Enter on it) opens the note; the details are behind the small ⓘ button. Failed and cancelled jobs still open the details.
- **Captured notes leave the inbox once written.** A note made through `obsidian://video-summary` loses its inbox heading and callout, the `video-summary/inbox` tag and its empty fields when processing succeeds.
- **Light-tier notes match backend notes.** Same prompt (v5), same temperature, the same note writer with default properties, CSS class and theme marks; a video keeps its own title as the note name (also when Obsidian has just started and has not read the note yet), and the extension sends the uploader, the duration (written as yt-dlp writes it) and the cover with the captions.
- **Model and keys have their own group** at the top of the settings page, used by both tiers, so a key alone is enough to start. With the light tier ready, a backend that was never installed shows as _not set up · light tier ready_ instead of an error.

- **You can see whether the backend is up.** The status bar shows a dot and a word (online, offline, checking, starting), and so does the top of the side panel. The plugin checks when Obsidian has loaded, when its window gets focus, and before each job, never in a tight loop. Click the dot for a check-up: Docker engine, container, service, workflow, with the one next step.
- **A job sent while the backend is off waits instead of being dropped.** It stays in the list as _Waiting for backend_ and starts by itself once the backend answers. You are told within a few seconds, not after a timeout.
- **Start backend.** For a backend on this computer, the notice, the side panel and the check-up have a _Start backend_ button. It opens OrbStack or Docker Desktop, starts the backend container, and waits up to 90 seconds for the webhook; if that fails it says where it stopped: Docker not installed, engine not up, container not starting, or workflow not answering. It only starts what is already installed and never downloads or updates anything. The folder with `compose.yaml` is remembered under **Settings → Video Summary → Backend folder**; an existing container is found by its port, so most setups never need it. Tested on macOS; Windows and Linux use the same commands and are untested.
- **"Empty response" now says which kind.** The plugin tells apart nothing listening at the address (the backend is not running), n8n running with the workflow switched off, a workflow that failed, and a workflow that answered with nothing, each with its own next step.
- **A long job no longer waits out the full timeout when the backend dies.** While a job runs, the plugin asks the backend every 45 seconds whether it is still there; two misses in a row fail the job at once with a Retry button. A backend that is shut down mid-job (n8n answers with an empty reply as it stops) is reported as "the backend stopped", not as a workflow error, and the jobs queued behind it wait instead of failing one by one.

- **Set up the backend from the settings page (macOS).** No zip, no start script, no connection code. Under **Settings → Video Summary → Backend**, choose the summary model, add the two keys and press **Install and start**. The plugin writes the backend folder (`~/video-summary-backend`) and opens Terminal, which shows the command and waits for you to press Return before downloading the backend image; the plugin never downloads or updates anything by itself. Back in Obsidian the page gives the backend its model and keys, runs the full check and a trial run, along one progress line. Before a backend exists the page shows only the step to do now. Windows keeps the start script and the connection code; the new flow is not tested there.
- **Model and keys live in settings.** Summary model (DeepSeek, SiliconFlow, Qwen, Kimi, Gemini, or your own address), summary key and speech-to-text key are chosen on the settings page. Keys are kept in Obsidian's secret storage (Obsidian 1.11.4 or newer). Changing them reaches the backend in about half a minute, with no `.env` edit. The plugin hands them over with `docker exec` on standard input, so they are in no command line, HTTP request or n8n execution record. Values in `.env` keep working and are the fallback.
- **A remote backend or your own n8n keeps its own credentials.** For such a backend the settings page says the model and keys there are used by the light tier only.
- **Changing the model does not fail jobs.** The backend restarts for about half a minute; the plugin waits for running jobs to finish first, and jobs sent meanwhile wait in the queue and start when the backend answers.
- **A backend installed with the start script is adopted as it is.** Its token, port, folder and `.env` keys stay; the connection code keeps working.
- **Update backend.** When the plugin is newer than the backend, the settings page says so and **Update backend** opens Terminal for the download, on your confirmation.
- The Backend group also has **Check**, **Stop**/**Start**, Bilibili login and **Start with the computer**. Other backends, the connection code, the backend folder and a mirror for the backend image moved under **Advanced**.

The plugin now runs the `docker` command line and can open Terminal; see **Programs the plugin runs** and **Files outside the vault** in the README. The bundled backend changed: `init/configure.mjs` takes the model and keys from the plugin. Update the backend to set them from settings; an older backend keeps working with its `.env`.
